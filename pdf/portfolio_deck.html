03 · 트러블슈팅 ① 데이터 정합성

동시 요청으로 외부 API가 중복 호출되고 결과가 덮어써지던 문제

문제
여러 상담사가 같은 참여자에 대해 동시에 'AI 직무 추천'을 누르면 Gemini API가 N번 중복 호출되어 비용과 지연이 쌓였고, 응답 순서에 따라 서로 다른 추천 결과가 DB에 덮어써졌습니다(race condition).
원인 분석
같은 participantId로 동시 요청 3건을 보내는 재현 스크립트를 만들어 매번 3건의 호출과 race가 일어나는 것을 확인했습니다. 서비스가 호출마다 새로 Gemini를 부르고 있었고, 중복을 걸러 낼 계층이 없었습니다. 트랜잭션 경계로는 외부 API 호출 자체를 막을 수 없었습니다.
해결
participantId를 키로 진행 중인 CompletableFuture를 공유하는 RecommendConcurrencyManager를 서비스 진입부에 얇은 게이트로 붙였습니다. 뒤따르는 요청은 새로 호출하지 않고 같은 Future를 받고, 완료나 예외가 나면 자동으로 정리됩니다.
결과
동일 참여자 중복 호출 100% 차단, 외부 API 비용과 지연 감소, 추천 결과 일관성 보장.
외부 의존성 호출의 비용과 일관성은 트랜잭션 경계 밖에서 별도 계층으로 다뤄야 한다는 것을 배웠습니다. AOP와 락, 캐시 중 어디에 책임을 둘지 분리해서 보는 습관을 얻었습니다.
// 핵심 아이디어
class RecommendConcurrencyManager {
  // participantId → 진행 중인 요청
  ConcurrentHashMap<Long, CompletableFuture<Result>> inflight;

  CompletableFuture<Result> runOrJoin(Long pid,
                                       Supplier<Result> task) {
    return inflight.computeIfAbsent(pid,
      k -> CompletableFuture.supplyAsync(task)
            .whenComplete((r, e) -> inflight.remove(k)));
  }
}

04 · 트러블슈팅 ② Redis 활용과 운영 부하

1분 폴링을 없애고 다중 WAS 알림을 Redis pub/sub으로 동기화

문제
상담사 화면이 1분 폴링과 수동 새로고침에 의존해 동시 접속자가 늘수록 DB 부하가 비례해 늘었고, 다중 WAS 환경에서는 한 노드의 알림이 다른 노드 사용자에게 전달되지 않았습니다.
원인 분석
폴링 간격을 줄이는 임시방편은 곧 부하 폭증으로 이어집니다. 단일 STOMP simple broker만으로는 인스턴스 사이 메시지가 격리되므로, 노드 안 브로커와 노드 간 pub/sub을 분리하는 구조가 맞다고 판단했습니다.
해결
/ws-notification STOMP/SockJS 엔드포인트를 새로 만들고 /topic·/app prefix로 알림 종류를 나눴습니다. 노드 간 동기화는 Redis pub/sub 채널로 처리하고 기존 폴링 로직을 제거해 이벤트 기반 push로 바꿨습니다.
결과
폴링 제거로 DB 조회 부하 감소, 다중 WAS 인스턴스 알림 동기화, 이후 알림 종류를 추가할 때 코드 수정이 거의 필요 없는 구조.
